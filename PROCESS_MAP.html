The shape of the system

Three tiers, and the boundary between them matters more than any single class. The browser tier never touches Net Zero Cloud objects; it only speaks JSON to BulkGapFillController. The controller does no gap logic; it validates, records, and enqueues. Everything that reads or writes NZC data lives in BulkGapFillBatch, and the arithmetic it applies lives in BulkGapFillService, which deliberately accepts no SObjects at all.

File Job Knows about NZC?
BulkGapFillService.cls Merge ranges, detect gaps, flag date issues, resolve a daily rate. Operates on DateRange / EnergyRecord wrappers. No — testable in an org without Net Zero Cloud
BulkGapFillConstants.cls Every object name, field name, method token, status token, unit conversion, plus validateSchema(). Names only
BulkGapFillBatch.cls Query scope, load supporting data, drive the service, build and insert records, roll up counters. Yes — the only class that queries NZC
BulkGapFillRequest.cls Run configuration DTO with validate(), methodFor(), and effective period bounds. No
BulkGapFillController.cls Six @AuraEnabled entry points. Owns job-row creation and the launch/abort lifecycle. One COUNT() for the scope preview
BulkGapFillJobScheduler.cls Schedulable wrapper. Deep-copies the stored request and resolves a null year to “last year”. No

One run, end to end

The sequence below is the whole product in one picture. Note where the thread of control breaks: launchRun returns a job id the moment the batch is enqueued, and everything after that reaches the user only because the Monitor polls. There is no push, no platform event — the wizard advances a step because a poll came back with a terminal AsyncApexJob status.

  1. 01

    Configure

    getConfigOptions is cacheable=true and returns the five fill methods, the last seven reporting years, live StationaryAssetType picklist entries, and — importantly — the output of validateSchema(). Any NZC name mismatch surfaces on this first screen, before a run is possible.

  2. 02

    Preview scope

    countFootprintsInScope runs a COUNT() using the same WHERE-clause construction as the batch’s start(). It is a scope sanity check, not a gap count — nothing is analysed yet.

  3. 03

    Launch

    launchRun validates, inserts the job row as Queued, enqueues the batch, then stamps AsyncApexJobId__c and FootprintsInScope__c. If anything throws after the insert, the row is flipped to Failed rather than left stuck at Queued.

  4. 04

    Batch runs

    start() marks the job Running and returns a QueryLocator. execute() fires once per chunk of 50 footprints. Counters live on the batch instance — Database.Stateful is what carries them across chunks into finish().

  5. 05

    Monitor

    A setTimeout chain calls getJobStatus every three seconds. Percent complete comes from AsyncApexJob.JobItemsProcessed / TotalJobItems; the footprint and record counts come from the job row the batch keeps updating. When the platform status is terminal the component waits 1.2s and fires runcomplete.

  6. 06

    Review

    finish() writes the roll-ups and the terminal status. Results pages BulkGapFillJobDetail__c 200 rows at a time, filterable by outcome, with a client-side CSV export of whatever rows are currently loaded.

Inside one chunk

execute() is where the governor limits are actually spent, and its structure is shaped entirely by them. Every query is hoisted above the footprint loop; every insert is deferred below it. The loop body itself does no DML and no SOQL.

The second thing to read for is the error containment — three nested layers, each with a different blast radius.

Why dynamic SOQL everywhere

NZC object and field API names vary by org edition and release, so every NZC query is built as a string from BulkGapFillConstants. A wrong name becomes a runtime error captured on the job record instead of a deploy failure that blocks the package. The cost is that a green deploy proves nothing about those names — which is exactly what validateSchema() exists to cover, and why its output is surfaced on the Configure screen.

How gaps are found

Gap detection is pure interval arithmetic, and it happens per fuel type — an electricity bill covering March does nothing for a natural-gas gap in March. For each fuel type the service clips existing records to the reporting period, merges them into a minimal covering set, then walks a cursor from the first day of the period and emits whatever the cursor skips over.

The four steps, in code order

analyzeFootprint groups records by FuelType, then per group: detectDateIssues flags missing, inverted, and overlapping periods; usable records become DateRanges; detectGaps clips them to the period, calls mergeRanges, and walks the cursor; the first non-blank FuelConsumptionUnit found is carried forward so generated records inherit the unit their siblings already use.

Two behaviours worth knowing before you trust a run

A fuel type with zero records is invisible unless you name it. Grouping starts from the records that exist, so a footprint with no gas bills at all produces no gas FuelGapSet — the whole year goes undetected. Listing the fuel type explicitly in the request forces an empty group into the map, which then reads as a whole-period gap.

Coverage does not distinguish estimates from actuals. loadEnergyRecords selects every energy use row on the footprint, including ones a previous run generated. So a repeat run over the same period generally finds the gaps already closed and writes No Gaps rows. That idempotence is incidental, not a guard — the intended guard, skipAlreadyFilled, is not wired up (see §7).

How a gap gets a number

Every method reduces to a single daily consumption rate, which is then multiplied by the gap’s inclusive day count. The batch assembles a FillContext per footprint × fuel type — only the fields the chosen method needs get populated — and hands it to resolveDailyRate.

Unit normalisation happens on read

Two conversions in BulkGapFillConstants keep the arithmetic in one unit system. toSquareMetres converts an asset’s OccupiedFloorArea when its unit reads as imperial and otherwise passes it through; toKwhPerSquareMetre prefers a benchmark’s AnnualIntensityValueInKwhM2 and falls back to converting the sqft column, so a benchmark with only the imperial figure populated stays usable. Both BEI lookups resolve against the same BldgEnrgyIntensity object, so one query over its child value records serves both methods.

Config → behaviour

BulkGapFillRequest is the contract between the wizard and the batch: the Configure component builds it as a plain object, JSON.stringifys it, and Apex deserializes it straight into the class. Because it round-trips as JSON and is stored on the job row, the request is also the run’s reproducibility record.

The table below is the honest version — including the three fields the UI collects that nothing downstream reads.

Field Consumed by Effect
reportingYear Scope query, prior-year lookup, period bounds Bound as text via reportingYearBind() — ReportingYear is a string column on the NZC objects, so an Integer bind throws at runtime.
periodStart / periodEnd effectivePeriodStart/End() Null means Jan 1 – Dec 31 of the reporting year. Set both for a fiscal year.
defaultFillMethod methodFor() → resolveDailyRate Required; validated against ALL_METHODS before launch.
manualDailyRate FillContext One rate for the whole run, not per asset. Required and non-negative when the method is Manual.
carbonFootprintIds buildFootprintQuery() Wins outright — when populated, year and asset filters are ignored entirely.
stationaryAssetIds, assetTypes buildFootprintQuery() ANDed onto the year filter. Asset type traverses StnryAssetEnvrSrc.StationaryAssetType.
fuelTypes analyzeFootprint() Empty means “every fuel type that has records”. Naming one forces a gap set even with zero records. Entered in the UI as free-text, comma-separated — no picklist, so a typo silently yields a whole-year gap.
isDryRun execute() Full detection and full audit trail, zero energy use inserts. Detail status becomes Preview.
batchSize launchRun Chunk size for Database.executeBatch, default 50, validated 1–2000.
methodOverrides methodFor() — Apex side works Not reachable from the UI. The Configure component always sends an empty map. Per-footprint methods are available only to an Apex or scheduled caller.
associateOrphans Nothing Not implemented. Surfaced as a checkbox and carried on the request, but no matching logic runs and RecordsAssociated__c stays at zero — including the tile the Monitor screen shows for it.
skipAlreadyFilled Nothing Not enforced. Defaults to true but execute() never reads it, so previously filled footprints are re-scanned rather than skipped. EnergyRecord.isGapFilled is already populated from IsSystemGeneratedRecord for whenever it is wired up.
Other live limitations

Aborting a run stops later chunks but does not roll back earlier inserts; and CSV export covers only the detail rows currently loaded in the grid, which pages at 200.

Two failure paths are knowingly untested: the chunk-level catch in execute(), and the partial-failure branch of Database.insert. Both need DML to fail against real NZC objects, and forcing that distorts the fixtures more than the coverage is worth.

The date convention is also a decision, not a given: this build treats ranges as inclusive at both ends, where the native wizard’s published formula uses EndDate - StartDate. Confirm which one your org’s audit expects before trusting the totals.

Running it

Deploy the source, assign Bulk_Gap_Fill_Admin — the permission set carries field-level security for both custom objects, and custom fields deploy with FLS off, so object access alone produces “fields being inaccessible” the moment a run launches. Then, before the first real run:

  1. 01

    Validate the schema

    Run scripts/apex/validate-schema.apex. Because the NZC queries are dynamic, a clean deploy proves nothing about the API names in BulkGapFillConstants. An empty result means the org is ready; anything listed is a one-file fix. The same output also appears on the Configure screen.

  2. 02

    Count the scope

    Use the scope preview to confirm the year and filters select the footprints you expect before committing to a run.

  3. 03

    Dry run first

    A dry run performs full gap detection and writes the complete per-asset audit trail without creating a single energy use record. Read the Skipped rows especially — a benchmark missing the fuel type being filled fails quietly there, and across a large portfolio that is easy to miss.

  4. 04

    Then run live

    Same configuration with the dry-run box cleared. Generated records carry IsSystemGeneratedRecord = true, the same flag the native process sets — so actuals-only reporting views should filter on it being false, and records from either route are counted consistently.

How this is verified

BulkGapFillBatchRunTest runs the batch against real Net Zero Cloud records and then reads the generated energy use rows back. That read is the point: a run can detect gaps, report Filled, and create nothing — which is exactly what a restricted picklist rejecting every insert looked like from the results grid. It covers all five fill methods, dry runs, year and asset-type scoping, and the skip paths.

BulkGapFillServiceTest, BulkGapFillRequestTest, BulkGapFillControllerTest, and BulkGapFillBatchTest need no NZC data and stay green in a scratch org without it, as do the four LWC Jest suites. Org-wide Apex coverage sits at 91%.
